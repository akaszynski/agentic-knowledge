# Knowledge entry format

Each numbered file in this directory records one problem and the smallest
useful, verified lesson that came from solving it. Entries are written for
people, search engines, and language models. A reader should be able to tell
what worked, where it worked, and how the result was checked without needing
the original conversation.

This format file is the schema description and is not itself a knowledge
entry.

## File names

Use `NN-kebab-case.md`, where `NN` gives the reading order. Keep one durable
lesson or closely related problem in each file.

## Front matter

Start each entry with this YAML front matter:

```yaml
---
title: "Short literal title"
summary: "One sentence stating the problem and verified outcome."
date: YYYY-MM-DD
last_verified: YYYY-MM-DD
status: draft
authorship: llm-generated
tags: [first-topic, second-topic]
environment: ["Relevant product and version", "Relevant platform"]
validation: observed
license: CC0-1.0
---
```

Use the following controlled values:

| Field | Values |
| --- | --- |
| `status` | `draft`, `verified`, or `superseded` |
| `authorship` | `llm-generated`, `human-written`, or `mixed` |
| `validation` | `reproduced`, `observed`, or `reasoned` |

`reproduced` means the result was repeated from the documented procedure.
`observed` means the result was directly checked at least once. `reasoned`
means the entry is an analysis that has not been exercised end to end. Use
`draft` while the entry awaits review even when its technical result was
observed. A superseded entry must link to its replacement near the top.

Text outside literal `<human>...</human>` tags is assumed to be generated by a
language model, as described in the repository README. Use those tags only for
words actually written by a person. Human review belongs in the validation
record; it does not change generated prose into human-authored prose.

## Entry sections

Use these sections in order. Omit a section only when it truly does not apply.

1. `# Title`
2. `## Outcome`
3. `## Problem`
4. `## Constraints and assumptions`
5. `## Approach`
6. `## Implementation`
7. `## Validation`
8. `## Failure modes and recovery`
9. `## Security and privacy`
10. `## Generalizable lessons`
11. `## References`

The outcome gives the direct answer in two to four sentences. The problem
records the observed behavior rather than a guess about its cause. Constraints
state the versions, authority, scope, and assumptions that bound the result.

The approach explains the architecture and the reason for it. Implementation
contains reproducible steps and copyable commands. Validation separates direct
observations from inference and includes the commands or measurements used.
Failure modes record recognizable symptoms and a safe way back. Security and
privacy identify the remaining trust boundaries and any details deliberately
generalized for publication.

Add `## What did not work` between Implementation and Validation when a failed
path teaches something distinct.

## Evidence and writing

Lead with the result. Prefer exact versions, filenames, configuration keys,
error messages, and verification commands over claims that something is
secure, reliable, or important. Keep one technical term for one object. Mark
observations, inferences, and recommendations as such, and do not strengthen a
claim beyond the available evidence.

Use direct links to primary documentation. Quote only when the exact wording
matters. CC0 applies to original prose in this repository, not to linked or
quoted third-party material.

Commands must identify where they run and use consistent placeholders such as
`<target-disk>` and `<certificate>`. Put a warning before destructive or
irreversible commands, show a read-only identity check first, and state the
recovery path.

## Public-safety rules

Remove details that do not help reproduce the lesson: customer and project
names, credentials, private keys, passphrases, personal contact information,
internal hostnames, private addresses, MAC addresses, serial numbers, and
private network topology. Replace a necessary machine-specific value with a
descriptive placeholder.

Describe security work as authorized administration, recovery, testing, or
hardening. Include enough mechanism to explain and reproduce the legitimate
result, but do not publish secrets or operational access details. State
remaining risks rather than implying that one successful test proves a general
security property.
